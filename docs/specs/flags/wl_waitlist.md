# Флаг: `-wl` / `-waitlist`

**Используется в:** [`/newevent`, `/editevent`](../commands/newevent_editevent.md) (в `/shareevent` есть свой override — `-swl`, см. спек команды)
**Синтаксис:** `-wl visible|hidden|onlycount` (или `-waitlist ...`)
**Тариф:** требует PRO (фича `event_limit`) — без него флаг отклоняется с ошибкой
**Дефолт:** `hidden`, если флаг не указан
**Значения:** см. [общий словарь `visible`/`hidden`/`onlycount`](./shared_visibility_vocab.md)

---

## Назначение

Управляет отображением листа ожидания (Waitlist) в посте события. Сама очередь работает всегда (если задан `-limit` и место заполнено) — флаг влияет только на видимость в посте, не на механику накопления очереди.

## Детальное поведение по значениям

1. **`hidden`** (дефолт) — Waitlist не отображается нигде в посте. Единственный способ увидеть — `/waitlist` (admin-only, игнорирует этот флаг).
2. **`onlycount`** — показывается только суммарное число ожидающих **по всем чатам сразу**. Цифра одинакова и в хабе, и в любом дочернем чате.
3. **`visible`** — здесь есть ключевое различие между хабом и дочерним чатом:
   - **В посте хаба:** список **всех** ожидающих по **всем** чатам, куда шарился ивент. Записи из дочерних чатов помечены `from <название чата>`.
   - **В посте дочернего чата:** только записи, добавленные именно из этого чата — без cross-chat записей и без пометки `from`.
   - Гостевые слоты группируются по владельцу — несколько слотов одного человека сливаются в одну строку с числом.

## Взаимодействие с другими флагами/фичами

- **`-limit`**: Waitlist имеет смысл только при заданном лимите, но `-wl` можно менять независимо в любой момент — не обязательно в той же команде, что `-limit`.
- **[`-clc`](./clc_clickability.md)**: отдельно решает, кликабельны ли имена внутри Waitlist-списка.
- **`/shareevent -swl`**: per-share override — конкретный дочерний чат может иметь своё значение `-wl`, отличное от события. Без override — наследует значение события.

## Тест-сценарии

- [ ] **T1 — Дефолт.** `/newevent Party` без `-wl` → `waitlist_visibility = 'hidden'`.
- [ ] **T2 — Явный выбор.** `/newevent Party -limit 10 -wl visible` → `waitlist_visibility = 'visible'`.
- [ ] **T3 — Гейтинг на FREE.** FREE-хаб, `-wl visible` → ошибка "requires a higher tier", изменение не применяется.
- [ ] **T4 — Гейтинг на PRO.** PRO-хаб, тот же вызов → применяется без ошибки.
- [ ] **T5 — `hidden`: рендер.** Есть 2 ожидающих → пост **не содержит** секции Waitlist вообще.
- [ ] **T6 — `onlycount`: рендер.** 3 ожидающих (2 в хабе + 1 в дочернем) → и хаб, и дочерний чат показывают одинаковую цифру `3`, без имён.
- [ ] **T7 — `visible` в хабе: cross-chat.** 1 ожидающий локально в хабе + 1 в дочернем чате → пост хаба показывает обоих, у дочернего — пометка `from <имя чата>`, у локального — без пометки.
- [ ] **T8 — `visible` в дочернем чате: изоляция.** Тот же сетап → пост дочернего чата показывает только своего локального ожидающего.
- [ ] **T9 — Группировка гостей.** Один человек занимает 3 гостевых слота подряд → в `visible`-рендере одна строка с числом `3`, не три отдельные.
- [ ] **T10 — `/waitlist` игнорирует флаг.** `-wl hidden`, есть ожидающие → `/waitlist` всё равно возвращает полный список.
- [ ] **T11 — Per-share override.** Событие `-wl hidden`, дочерний чат расшарен с `-swl visible` → именно этот дочерний чат показывает Waitlist, несмотря на `hidden` у события.
- [ ] **T12 — Изменение на лету.** Событие открыто с `-wl hidden`, есть накопленная очередь → `/editevent -wl visible` → пост обновляется и показывает уже накопленную очередь, не только новых.
- [ ] **T13 — Понижение `-limit` ниже текущего headcount.** Если одновременно меняется `-limit` на значение ниже текущего суммарного числа участников (хаб + все дочерние) → изменение **отклоняется целиком** (лимит остаётся прежним), `-wl` из той же команды при этом тоже не применяется, так как вся команда завершается с ошибкой до записи в БД.
